# 圃場記録アプリ 画面設計

## 1. 目的

本書では、MITSURU FARM
圃場記録アプリの初期版SPAについて、画面構成、画面遷移、各画面の表示項目、入力項目、主要操作を定義する。

本設計は以下を前提とする。

-   個人利用
-   スマートフォンを主端末とする
-   PCでも利用可能
-   オンライン専用
-   APIは `docs/API設計.md` を利用する
-   データ構造は
    `docs/データ設計.md`、`docs/テーブル構成設計.md`、`docs/DynamoDB詳細設計.md`
    に従う

------------------------------------------------------------------------

## 2. 画面設計の基本方針

### 2.1 モバイルファースト

農作業中にスマートフォンで利用することを想定し、以下を基本とする。

-   片手でも操作しやすい
-   入力項目を必要以上に増やさない
-   ボタンを大きめにする
-   一覧では重要情報を先に表示する
-   詳細情報は画面を分けて表示する
-   作業記録・収穫記録を少ない操作で登録できるようにする

### 2.2 階層構造をそのまま画面構造へ反映

``` text
ホーム
  ├─ 現在栽培中
  │    └─ 栽培詳細
  │         ├─ 作業
  │         ├─ 収穫
  │         └─ 写真
  │
  └─ 圃場
       └─ 圃場詳細
            └─ エリア詳細
                 └─ 栽培履歴
                      └─ 栽培詳細
```

### 2.3 「記録する」と「見る」を分離

主要操作は以下の2種類に整理する。

-   見る：一覧・詳細・履歴
-   記録する：栽培・作業・収穫・写真の登録

## 24. 削除確認

物理削除を行う対象では、削除前に確認ダイアログを表示する。

### 通常削除

``` text
「この作業記録を削除しますか？」

[キャンセル] [削除]
```

### 配下データが存在する削除

``` text
「10a圃場を削除しますか？」

この圃場に含まれる以下のデータも削除されます。

・エリア
・栽培記録
・作業記録
・収穫記録
・写真

[キャンセル] [削除する]
```

CROPの削除は「削除」ではなく「利用停止」として表示する。

## 26. ローディング・空状態・エラー

### ローディング

一覧取得中はスピナーまたは簡易ローディング表示を行う。

### データなし

例：

``` text
栽培中の作物はありません。
```

``` text
作業記録はまだありません。
[＋作業を記録]
```

### APIエラー

APIの統一エラー形式を画面用メッセージへ変換する。

``` text
保存できませんでした。
もう一度試してください。
```

技術的な内部エラー詳細は画面へ表示しない。

## 27. ページング

一覧APIはAPI設計に従い、

-   初期表示：50件
-   最大：100件
-   続きがある場合：`nextToken`

を使用する。

スマートフォンでは「次の50件を表示」または無限スクロールを採用できる。

初期実装では実装が単純な「次のページ」方式を基本とする。

## 28. 初期版での入力体験

## 31. 初期版で画面に実装しないもの

以下は現時点では初期版の必須画面に含めない。

-   オフライン入力
-   高度なダッシュボード・グラフ
-   売上・経費分析
-   作業時間の高度な集計
-   天候APIとの自動連携
-   地図上への圃場表示
-   Dropboxフォルダ管理画面
-   複数ユーザー向け権限管理
-   高度な検索条件
-   CSV入出力

必要性が確認できた段階で追加設計する。

## 32. 画面設計上の重要な設計判断

### 32.1 栽培詳細を中心画面とする

農業記録では、作業・収穫・写真がすべて特定の栽培に紐付くため、栽培詳細を中心にする。

``` text
CULTIVATION
 ├─ WORK_LOG
 ├─ HARVEST
 └─ PHOTO
```

### 32.2 ホームは「現在栽培中」を中心にする

日常的には過去履歴よりも「今何を育てているか」を確認する頻度が高いため、ホームでは現在栽培中を最優先する。

### 32.3 入力画面は最小入力を優先する

農作業中にすべての項目を入力することを前提とせず、必須項目を少なくする。

### 32.4 詳細画面から直接記録できるようにする

栽培詳細から、

-   作業追加
-   収穫追加
-   写真追加

へ直接進めるようにする。

## 33. API URL階層との整合

API設計では、DynamoDBの親子関係と整合させるため、子リソースの詳細・更新・削除APIに必要な親IDをURLへ含める方式（A）を採用する。

### 確定したURL

```text
AREA
GET    /api/v1/fields/{fieldId}/areas/{areaId}
PUT    /api/v1/fields/{fieldId}/areas/{areaId}
DELETE /api/v1/fields/{fieldId}/areas/{areaId}

AREA → CULTIVATION
GET    /api/v1/fields/{fieldId}/areas/{areaId}/cultivations

WORK_LOG
GET    /api/v1/cultivations/{cultivationId}/work-logs/{workLogId}
PUT    /api/v1/cultivations/{cultivationId}/work-logs/{workLogId}
DELETE /api/v1/cultivations/{cultivationId}/work-logs/{workLogId}

HARVEST
GET    /api/v1/cultivations/{cultivationId}/harvests/{harvestId}
PUT    /api/v1/cultivations/{cultivationId}/harvests/{harvestId}
DELETE /api/v1/cultivations/{cultivationId}/harvests/{harvestId}

PHOTO
GET    /api/v1/cultivations/{cultivationId}/photos/{photoId}
DELETE /api/v1/cultivations/{cultivationId}/photos/{photoId}
```

CROPは独立したマスターデータのため、従来どおりトップレベルのリソースとして扱う。

この変更はAPIのURL階層を確定するものであり、DynamoDBのPK/SK/GSI設計は変更しない。
