# 圃場記録アプリ テーブル構成設計書

## 1. 概要

個人利用を想定した農業・圃場記録アプリのデータ構成設計。

### 想定アーキテクチャ

- フロントエンド: GitHub Pages 上のSPA
- API: API Gateway + AWS Lambda
- データベース: Amazon DynamoDB
- 写真: Dropbox
- 作物: 作物マスタで管理

## 2. 基本データ構造

データの概念上の関係は以下とする。

```text
圃場 (FIELD)
 └─ エリア (AREA)
     └─ 栽培 (CULTIVATION)
         ├─ 作業履歴 (WORK_LOG)
         ├─ 収穫記録 (HARVEST)
         └─ 写真情報 (PHOTO)

作物マスタ (CROP)
 └─ 栽培 (CULTIVATION) から cropId で参照

採番管理 (COUNTER)
 └─ 各IDの自動発番を管理
```

## 3. ID設計

IDはシステムで自動発番する。

| 種別 | プレフィックス | 例 | 説明 |
|---|---|---|---|
| 圃場ID | F | F0001 | 圃場を一意に識別 |
| エリアID | A | A0001 | エリアを一意に識別 |
| 栽培ID | C | C0001 | 1回の栽培を一意に識別 |
| 作業記録ID | W | W0001 | 作業記録を一意に識別 |
| 収穫記録ID | H | H0001 | 収穫記録を一意に識別 |
| 作物ID | P | P0001 | 作物マスタを一意に識別 |
| 写真ID | PH | PH0001 | 写真情報を一意に識別 |

番号部分は4桁ゼロ埋めとする。

例:

```text
F0001
F0002
A0001
C0001
C0002
```

採番はDynamoDBのCOUNTERレコードを利用し、LambdaからAtomic Counter方式で発番する。

## 4. 圃場 (FIELD)

圃場そのものの情報を管理する。

### 主な項目

| 項目 | 型 | 必須 | 説明 |
|---|---|---:|---|
| fieldId | String | ○ | 圃場ID |
| name | String | ○ | 圃場名 |
| area | Number | ○ | 面積 |
| location | String | △ | 所在地 |
| latitude | Number | △ | 緯度 |
| longitude | Number | △ | 経度 |
| soilType | String | △ | 土質 |
| drainage | String | △ | 排水性 |
| sunlight | String | △ | 日当たり |
| status | String | ○ | 使用中・休止等 |
| note | String | △ | 備考 |
| createdAt | String | ○ | 作成日時 |
| updatedAt | String | ○ | 更新日時 |

例:

```json
{
  "type": "FIELD",
  "fieldId": "F0001",
  "name": "10a圃場",
  "area": 1000,
  "location": "韮崎市",
  "drainage": "poor",
  "status": "active",
  "note": "元水田。雨後に一部水が溜まる"
}
```

| status | String | ○ | 使用中・休止等 |
| note | String | △ | 備考 |
| createdAt | String | ○ | 作成日時 |
| updatedAt | String | ○ | 更新日時 |

例:


### 主な項目

| 項目 | 型 | 必須 | 説明 |
|---|---|---:|---|
| cropId | String | ○ | 作物ID |
| name | String | ○ | 作物名 |
| category | String | △ | 根菜・葉菜等 |
| active | Boolean | ○ | 選択可能か |
| note | String | △ | 備考 |
| createdAt | String | ○ | 作成日時 |

## 7. 栽培 (CULTIVATION)

「どのエリアで、どの年度に、どの作物を育てたか」を管理する。

同じエリアでも年度が変われば別の栽培レコードを作成する。

### 主な項目

| 項目 | 型 | 必須 | 説明 |
|---|---|---:|---|
| cultivationId | String | ○ | 栽培ID |
| fieldId | String | ○ | 圃場ID |
| areaId | String | ○ | エリアID |
| cropId | String | ○ | 作物ID |
| year | Number | ○ | 栽培年度 |
| variety | String | △ | 品種 |
| season | String | △ | 作型・季節 |
| sowingDate | String | △ | 播種日 |
| plantingDate | String | △ | 定植日 |
| harvestStartDate | String | △ | 収穫開始日 |
| harvestEndDate | String | △ | 収穫終了日 |
| completedDate | String | △ | 栽培完了日 |
| status | String | ○ | planned/growing/completed/failed |
| note | String | △ | 備考 |
| createdAt | String | ○ | 作成日時 |
| updatedAt | String | ○ | 更新日時 |

### 栽培ステータス

| status | 意味 |
|---|---|
| planned | 栽培予定 |
| growing | 栽培中 |
| completed | 栽培完了 |
| failed | 栽培中止・失敗 |

`status = growing` を現在栽培中、`status = completed` を過去の完了栽培として扱う。

`completedDate` は完了時に設定する。

## 12. Dropbox保存方針

Dropboxのフォルダ構成案:

```text
MITSURU FARM/
├── F0001_10a圃場/
│   ├── A0001_Aエリア/
│   │   ├── 2026/
│   │   │   └── C0001_大根/
│   │   │       ├── 作業/
│   │   │       └── 収穫/
│   │   └── 2027/
│   └── A0002_Bエリア/
└── F0002_自宅畑/
```

アプリからDropbox APIを利用し、Lambda経由で写真のアップロード・参照情報の登録を行う。

## 13. データ検索要件

最低限、以下の検索を実現する。

### 圃場から検索

```text
圃場
 → エリア
 → 年度
 → 栽培
 → 作業履歴・収穫記録
```

### エリアから検索

```text
エリア
 → 年度
 → 栽培
 → 作業履歴・収穫記録
```

### 作物から検索

```text
作物
 → 年度
 → 圃場
 → エリア
 → 栽培
 → 作業履歴・収穫記録
```

### 現在栽培中

```text
status = growing
```

### 完了済み

```text
status = completed
```

## 14. DynamoDB設計について

現時点では、概念データモデルを確定した段階とする。

DynamoDBの物理設計では、上記検索要件を満たすために以下を検討する。

- 1テーブル方式
- PK / SK
- GSIによる作物からの逆引き
- 年度による検索
- 現在栽培中の検索
- ID採番用COUNTER
- Lambdaからのアクセス方式

物理的なPK/SK/GSIの確定は、次工程の「DynamoDB詳細設計」で行う。
