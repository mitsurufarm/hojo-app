# システム概要

## 1. システムの目的

MITSURU FARMで使用する個人向けの圃場・栽培記録アプリ。

圃場、エリア、作物、栽培、作業、収穫、写真などの情報を一元管理し、過去の栽培履歴を検索・参照できるようにする。

主な目的は以下のとおり。

- 圃場を管理する
- 圃場内をエリア単位で管理する
- エリアごとに栽培する作物を管理する
- 年ごとの栽培履歴を記録する
- 作業内容を記録する
- 収穫量を記録する
- 栽培・作業・収穫に関連する写真を管理する
- 過去の栽培履歴を検索する

本システムは現時点では個人利用を前提とし、MITSURU FARMの農業記録を管理するために使用する。

---

## 2. システムの基本構成

システムは以下の構成とする。

```text
スマートフォン / PC
        │
        ▼
GitHub Pages
SPA（Webアプリ）
        │
        ▼
Amazon Cognito
認証
        │
        ▼
Amazon API Gateway
        │
        ▼
AWS Lambda
        │
        ├──────────────┐
        ▼              ▼
Amazon DynamoDB    Dropbox API
構造化データ       写真ファイル
```

### 各サービスの役割

| サービス | 役割 |
|---|---|
| GitHub Pages | Webアプリ（SPA）の公開 |
| Amazon Cognito | ユーザー認証 |
| Amazon API Gateway | SPAからLambdaへのAPI入口 |
| AWS Lambda | API処理、データ処理、Dropbox連携 |
| Amazon DynamoDB | 圃場・栽培・作業・収穫などのデータ保存 |
| Dropbox | 写真ファイルの保存 |

---

## 3. 利用形態

### 3.1 個人利用

現時点では個人利用を前提とする。

複数ユーザーでの共同利用やユーザーごとの細かな権限管理は初期開発の対象外とする。

ただし、将来的な拡張を妨げない設計を意識する。

### 3.2 オンライン専用

オフライン利用には対応しない。

通信できない状態での入力・保存・後からの同期処理などは初期バージョンでは実装しない。

---

## 4. 認証

Amazon Cognitoを使用する。

ログインが必要なユーザーのみアプリを利用できるようにする。

認証情報やAWSの認証情報をSPA側に直接埋め込まない。

```text
ユーザー
  ↓
Cognito
  ↓
認証
  ↓
SPA
  ↓
API Gateway
  ↓
Lambda
```

## 5. データ管理の基本構造

データは以下の階層で管理する。

```text
FIELD（圃場）
  │
  ├── AREA（エリア）
  │      │
  │      └── CULTIVATION（栽培）
  │              │
  │              ├── WORK_LOG（作業記録）
  │              ├── HARVEST（収穫記録）
  │              └── PHOTO（写真）
  │
  └── AREA
```

作物はCROP（作物マスタ）で管理し、CULTIVATIONから参照する。

```text
CROP（作物マスタ）
      │
      ▼
CULTIVATION（栽培）
```

---

## 6. 各データの役割

### FIELD（圃場）

実際に使用する圃場そのものを管理する。

例：

```text
F0001
10a圃場
```

圃場名、面積、場所、土質、水はけ、日当たりなどを管理する。

### AREA（エリア）

1つの圃場を分割して管理するための単位。

例えば10aの圃場を複数のエリアに分け、それぞれ異なる作物を栽培できるようにする。

```text
F0001
└── A0001
    └── Aエリア
```

同じエリアは翌年以降も再利用できる。

### CROP（作物マスタ）

作物名をマスタ管理する。

例：

```text
P0001 大根
P0002 白菜
P0003 玉ねぎ
```

栽培記録では自由入力で作物名を登録せず、CROPを参照する。

### CULTIVATION（栽培）

「どの圃場のどのエリアで、何年に、何の作物を栽培したか」を管理する。

同じAREAであっても、年度や作物が変われば別のCULTIVATIONとして記録する。

例：

```text
A0001
│
├── C0001 2026年 大根
├── C0002 2027年 玉ねぎ
└── C0003 2028年 白菜
```

栽培状態を管理する。

- `planned`：栽培予定
- `growing`：栽培中
- `completed`：栽培完了
- `failed`：栽培失敗

栽培完了時にはcompletedDateを記録する。

### WORK_LOG（作業記録）

栽培に関連する作業を記録する。

例：

```text
W0001
2026-09-05
草刈り
120分
```

作業内容、作業時間、人数、使用資材、使用道具、天候、土壌状態などを記録できるようにする。

初期の作業種別は以下を想定する。

- 耕起
- 整地
- 畝立て
- 草刈り
- 除草
- 播種
- 育苗
- 定植
- 間引き
- 追肥
- 土寄せ
- 灌水
- 防除
- 支柱立て
- 誘引
- 収穫
- 選別
- 出荷
- 片付け
- 草マルチ
- 緑肥播種
- 緑肥刈取り
- 米ぬか施用
- 堆肥施用
- その他

### HARVEST（収穫記録）

収穫した作物の数量などを記録する。

例：

```text
H0001
2026-12-01
大根
20kg
```

以下のような情報を管理する。

- 収穫日
- 収穫量
- 単位
- 販売数量
- 自家消費数量
- 廃棄数量
- 売上
- 販路

### PHOTO（写真）

栽培・作業・収穫などに関連する写真を管理する。

写真ファイル本体はDropboxに保存する。

DynamoDBには写真のメタデータとDropbox上の保存先を記録する。

```text
SPA
 ↓
API Gateway
 ↓
Lambda
 ├── DynamoDB
 │     └── PHOTO情報
 │
 └── Dropbox API
       └── 写真ファイル
```

初期バージョンでは、スマートフォンやPCから既存の写真ファイルを選択してアップロードする方式とする。

アプリから直接カメラを起動して撮影する機能は初期開発の対象外とする。

---

## 7. ID設計

各データには自動採番されたIDを付与する。

4桁のゼロ埋めとし、データ種別ごとにプレフィックスを付ける。

| データ | ID例 |
|---|---|
| FIELD | F0001 |
| AREA | A0001 |
| CROP | P0001 |
| CULTIVATION | C0001 |
| WORK_LOG | W0001 |
| HARVEST | H0001 |
| PHOTO | PH0001 |

IDはDynamoDBのAtomic Counterを利用して採番する。

最大値を取得して1を加算する方式ではなく、DynamoDBのアトミックなカウンター更新によって重複を防止する。

---

## 8. 写真管理

写真ファイルはDropboxに保存する。

Dropbox上では、圃場・エリア・年度・栽培単位などで整理する。

例：

```text
MITSURU FARM/
└── F0001_10a圃場/
    └── A0001_Aエリア/
        └── 2026/
            └── C0001_大根/
                ├── 作業/
                └── 収穫/
```

DynamoDBのPHOTOには、Dropbox上のファイルパスなどを保存する。

Dropboxのアクセストークンなどの認証情報はSPAには公開せず、Lambda側で安全に管理する。

---

## 9. 削除方針

データの削除は物理削除とする。

論理削除用のdeletedフラグなどは初期バージョンでは使用しない。

PHOTOを削除する場合は、以下を実行する。

```text
PHOTO削除要求
      │
      ├── DynamoDBのPHOTOレコード削除
      │
      └── Dropboxの写真ファイル削除
```

関連データを削除する場合の整合性については、API設計・DynamoDB詳細設計で定義する。

## 14. 設計方針

本システムでは、以下の方針を基本とする。

### シンプルな構成

個人利用が目的であるため、必要以上に複雑な構成にはしない。

### 低コスト

AWSなどのクラウドサービスを利用しつつ、個人利用で過剰なコストが発生しない構成を目指す。

### スマートフォンとPCの両対応

日常の畑作業ではスマートフォンから利用し、詳細な管理やデータ確認ではPCからも利用できるようにする。

### 栽培履歴を蓄積する

同じ圃場・エリアを長期間使用することを前提とし、年度ごとの栽培履歴を蓄積できるようにする。

### 作物をマスタ管理する

作物名を自由入力だけで管理せず、CROPマスタを使用して表記ゆれを防止する。

### 写真と記録を紐付ける

写真を単独で保存するのではなく、圃場・エリア・栽培・作業・収穫などの記録と関連付ける。

### AWSとDropboxの役割を分離する

構造化された農業データはDynamoDB、写真ファイルはDropboxに保存する。

### 将来の拡張を考慮する

初期段階では個人利用に必要な機能に絞るが、将来的な収支管理・栽培分析・作業管理などを追加できる設計とする。
