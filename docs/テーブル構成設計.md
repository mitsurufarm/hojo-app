# 圃場記録アプリ テーブル構成設計

## 1. 概要

本書では、`docs/データ設計.md` で定義した概念データモデルを、Amazon
DynamoDBの1テーブル方式へ落とし込む。

対象システムはMITSURU
FARMの個人利用を前提とし、以下のアクセスパターンを優先する。

-   圃場からエリア・年度・栽培履歴を参照する
-   エリアから年度・栽培履歴を参照する
-   作物から栽培履歴を逆引きする
-   現在栽培中の栽培を一覧する
-   栽培から作業・収穫・写真を参照する
-   IDを一意に自動採番する

DynamoDBではアクセスパターンを先に定義し、それに合わせてPK/SKとGSIを設計する。今回のアプリでは関連データを同一のItem
Collectionにまとめ、複合ソートキーによる階層検索を利用する。

------------------------------------------------------------------------

## 2. テーブル方式

### 2.1 採用方式

**DynamoDB 1テーブル方式**を採用する。

``` text
MITSURU_FARM_TABLE
│
├─ FIELD
├─ AREA
├─ CROP
├─ CULTIVATION
├─ WORK_LOG
├─ HARVEST
├─ PHOTO
└─ COUNTER
```

すべて同一のDynamoDBテーブルに格納し、`type`
属性によってデータ種別を識別する。

### 2.2 採用理由

-   個人利用でデータ量が比較的小さい
-   FIELD → AREA → CULTIVATION → WORK_LOG / HARVEST /
    PHOTOという階層構造が明確
-   圃場単位で関連データをまとめて取得しやすい
-   GSIによって作物・栽培状態など別の検索軸を追加できる
-   テーブル数を増やさず管理を単純化できる

------------------------------------------------------------------------

## 3. 基本キー設計

### 3.1 共通キー

  項目   内容
  ------ ------------------------------
  PK     DynamoDBのパーティションキー
  SK     DynamoDBのソートキー
  type   データ種別

基本的には、**FIELDを起点とした階層をPK/SKで構成する**。

### 3.2 基本構造

``` text
PK = F0001
SK = FIELD

PK = F0001
SK = AREA#A0001

PK = F0001
SK = AREA#A0001#CULTIVATION#2026#C0001

PK = F0001
SK = AREA#A0001#CULTIVATION#2026#C0001#WORK#2026-09-05#W0001

PK = F0001
SK = AREA#A0001#CULTIVATION#2026#C0001#HARVEST#2026-12-01#H0001

PK = F0001
SK = AREA#A0001#CULTIVATION#2026#C0001#PHOTO#PH0001
```

この構造により、圃場単位のItem Collectionに関連データを集約する。

### 3.3 IDとキーの役割

IDは業務上の一意識別子として使用し、DynamoDBのPK/SKは検索のための物理キーとして使用する。

例えば、`C0001`
は栽培IDそのものを表すが、ベーステーブルでは以下のように圃場・エリア・年度を含むSKに配置する。

``` text
AREA#A0001#CULTIVATION#2026#C0001
```

これにより、同じエリアの年度別栽培履歴をSKの範囲として取得できる。

## 5. FIELD

### 5.1 キー

``` text
PK = F0001
SK = FIELD
```

### 5.2 主な属性

  属性        型         必須 内容
  ----------- -------- ------ ----------------
  type        String        ○ `FIELD`
  fieldId     String        ○ 圃場ID
  name        String        ○ 圃場名
  area        Number        ○ 面積。m²で保存
  location    String        △ 所在地
  latitude    Number        △ 緯度
  longitude   Number        △ 経度
  soilType    String        △ 土質
  drainage    String        △ 排水性
  sunlight    String        △ 日当たり
  status      String        ○ 圃場状態
  note        String        △ 備考
  createdAt   String        ○ 作成日時
  updatedAt   String        ○ 更新日時

### 5.3 面積単位

DynamoDBには数値としてm²を保存する。

``` text
1000 m² = 10 a
300 m²  = 3 a
100 m²  = 1 a
```

画面表示では以下のようにm²とaを併記できるようにする。

``` text
1,000 m²（10a）
300 m²（3a）
```

aへの換算値をDynamoDBに別属性として保存する必要はない。

換算式:

``` text
a = m² ÷ 100
```

`year` は**栽培開始年**とする。

``` text

```

  planned     栽培予定
  growing     栽培中
  completed   栽培完了
  failed      栽培中止・失敗

`status = growing`
のCULTIVATIONだけに現在栽培中検索用GSIキーを設定する。

## 12. COUNTER

### 12.1 キー

``` text
PK = COUNTER
SK = F
```

例えば以下のように管理する。

``` text
COUNTER / F   → 15
COUNTER / A   → 23
COUNTER / P   → 8
COUNTER / C   → 42
COUNTER / W   → 180
COUNTER / H   → 70
COUNTER / PH  → 320
```

### 12.2 採番方式

LambdaからDynamoDBのAtomic
Counter方式で番号を加算し、その結果を4桁ゼロ埋めする。

``` text
ADD counterValue :increment
```

最大値を取得してから+1する方式は採用しない。

具体的なUpdateItemの条件やエラー処理は「DynamoDB詳細設計」で定義する。

## 13. GSI構成

初期バージョンでは、以下の3つのGSIを使用する。

  ------------------------------------------------------------------------------------------
  GSI                     目的                                       対象
  ----------------------- ------------------------------------------ -----------------------
  GSI1                    栽培単位で作業・収穫・写真をまとめて取得   CULTIVATION関連項目

  GSI2                    作物から栽培を逆引き                       CULTIVATION

  GSI3                    現在栽培中の栽培を一覧                     `status = growing`
                                                                     のCULTIVATION
  ------------------------------------------------------------------------------------------

------------------------------------------------------------------------

## 14. GSI1：栽培単位検索

### 14.1 目的

CULTIVATION詳細画面で、以下を一度のQueryで取得できるようにする。

``` text
CULTIVATION
├─ WORK_LOG
├─ HARVEST
└─ PHOTO
```

### 14.2 キー

``` text
GSI1PK = C0001
GSI1SK = 00#CULTIVATION
```

関連項目は以下のようにする。

``` text
GSI1PK = C0001
GSI1SK = 00#CULTIVATION

GSI1PK = C0001
GSI1SK = 10#WORK#2026-09-05#W0001

GSI1PK = C0001
GSI1SK = 20#HARVEST#2026-12-01#H0001

GSI1PK = C0001
GSI1SK = 30#PHOTO#PH0001
```

これにより、`GSI1PK = C0001` で栽培に関連する項目を取得できる。

------------------------------------------------------------------------

## 15. GSI2：作物からの逆引き

### 15.1 目的

以下の検索を実現する。

``` text
作物
 ↓
年度
 ↓
圃場
 ↓
エリア
 ↓
栽培
```

### 15.2 キー

CULTIVATIONだけにGSI2キーを設定する。

``` text
GSI2PK = CROP#P0001
GSI2SK = 2026#F0001#A0001#C0001
```

例えば大根 `P0001` の栽培履歴は、

``` text
CROP#P0001
├─ 2026#F0001#A0001#C0001
├─ 2027#F0002#A0003#C0012
└─ 2028#F0001#A0002#C0025
```

のように取得できる。

------------------------------------------------------------------------

## 16. GSI3：現在栽培中

### 16.1 目的

`status = growing` の栽培だけを一覧する。

### 16.2 キー

``` text
GSI3PK = STATUS#growing
GSI3SK = 2026#F0001#A0001#C0001
```

`planned`、`completed`、`failed` のCULTIVATIONにはGSI3キーを設定しない。

これにより、現在栽培中のデータだけを対象とするSparse GSIになる。

## 19. 削除方針との関係

システム概要で定義したとおり、削除は物理削除とする。

### FIELD削除

FIELDを削除する場合、配下の以下のデータも削除対象になる。

``` text
FIELD
├─ AREA
├─ CULTIVATION
├─ WORK_LOG
├─ HARVEST
└─ PHOTO
```

PHOTOについてはDynamoDBレコードだけでなくDropbox上のファイルも削除する。

### AREA削除

``` text
AREA
├─ CULTIVATION
├─ WORK_LOG
├─ HARVEST
└─ PHOTO
```

### CULTIVATION削除

``` text
CULTIVATION
├─ WORK_LOG
├─ HARVEST
└─ PHOTO
```

を削除対象とする。

### PHOTO削除

``` text
DynamoDB PHOTO削除
        +
Dropboxファイル削除
```

関連データ削除時の具体的なAPI処理順序、失敗時の扱い、条件付き削除などは「API設計」「DynamoDB詳細設計」で定義する。

## 20. データ重複方針

DynamoDBでは検索効率を優先して、親IDなどの属性を子Itemにも保持する。

例えばWORK_LOGには、

``` text
fieldId
areaId
cultivationId
```

をすべて保持する。

これはRDBの正規化を目的とするものではなく、DynamoDBのアクセスパターンに合わせて必要な検索情報をItemに持たせるためである。

ただし、親データの名称などは重複保存しない。

例えば、WORK_LOGに

``` text
fieldName
areaName
cropName
```

を保存することは基本的に行わない。

------------------------------------------------------------------------

## 21. キー設計上のルール

以下を基本ルールとする。

1.  PK/SKには階層検索に必要なプレフィックスを付ける。
2.  SKは親 → 子 → 年度 → IDの順で構成する。
3.  年度は4桁で保持する。
4.  日付はISO 8601形式の`YYYY-MM-DD`を使用する。
5.  時刻はISO 8601形式のUTC日時を使用する。
6.  IDは既定の4桁ゼロ埋め形式を使用する。
7.  GSIは明確なアクセスパターンが存在する場合だけ追加する。
8.  FilterExpressionだけで主要な検索要件を実現する設計は避ける。

------------------------------------------------------------------------

## 22. 面積の単位ルール

面積はすべてm²を正規値とする。

  用途      保存値 表示例
  ------- -------- -----------------
  FIELD       1000 1,000 m²（10a）
  AREA         200 200 m²（2a）
  AREA          30 30 m²（0.3a）

換算:

``` text
a = m² ÷ 100
m² = a × 100
```
